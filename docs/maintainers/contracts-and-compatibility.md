# Contracts and Compatibility

本文定义公共契约、兼容判断和版本等级。具体版本行为仍以版本匹配的公开声明、源码和测试为准。

## 1. 事实来源

维护本仓库时按以下顺序确认行为：

1. `src/index.ts` 的公共出口；
2. 目标实现和类型；
3. 最近的类型测试与 Jest 测试；
4. 对应 API 文档；
5. README、示例和 CHANGELOG。

处理消费项目时，先从 package、锁文件和实际解析位置确认安装版本，再读取该版本的公开声明、源码和测试。不要用本仓库最新行为解释其他版本。

## 2. 公共契约

默认属于公共契约：

- 包入口导出的运行时符号和类型；
- 四个组件构建 API 的合法调用形状；
- 用户可观察的 `ComponentDoc`、`PageDoc` 和实例类型；
- 公共事件标签、`DetailedType`、`typeEqual`；
- `instanceConfig` 的设置与覆盖语义；
- 类型化导航的参数、编码和回传语义；
- 文档承诺且由当前实现或测试支持的运行时行为。

不默认属于公共契约：

- 未从包入口导出的内部类型和深路径；
- 文件布局与内部函数拆分；
- computed/watch/store 的缓存结构；
- 测试 fixture 和覆盖率辅助字段；
- 消费项目的目录、样式和业务字段；
- 未被当前版本实现支持的历史示例。

内部实现若被 `vscode-annil` 等外部工具读取，可能形成跨仓库协议，不能仅凭“未导出”判断无影响。

## 3. 类型契约同样受 SemVer 约束

以下变化可能破坏消费项目，即使运行时不变：

- 原本合法的配置变为类型错误；
- 字段变窄、变宽、变为可选或必选；
- `this`、`this.data`、`setData` 或事件参数变化；
- 组件文档、前缀、事件标签或必传规则变化；
- 声明文件无法由支持范围内的 TypeScript 解析；
- 类型复杂度使典型组件无法完成检查。

不能以“只改类型”作为 patch 的充分依据。

## 4. 版本等级

通常属于 breaking：

- 删除或重命名公共导出；
- 改变 API 调用层级或必填参数；
- 让已有合法配置失效；
- 改变组件文档、前缀或公开实例形状；
- 改变已承诺的生命周期、响应式、导航或注入语义；
- 提高 TypeScript、微信类型或 peer dependency 最低要求。

通常属于 minor：

- 新增向后兼容的公共 API；
- 新增不改变旧推导的可选配置；
- 扩展第三方组件的可选类型；
- 新增不影响既有流程的能力。

通常属于 patch：

- 修复与既有契约不符的运行时或类型错误；
- 修正文档与当前公共出口的不一致；
- 公共声明、可观察行为和性能边界不变的内部重构。

类型修复仍应在发布说明中描述受影响的代码形状。

## 5. 跨仓库协议

Annil 的源码和运行时不读取所有外部工具约定。以下信息仍可能构成跨仓库协议：

- `vscode-annil` 对组件调用 AST、组件文档形状和字段前缀的解析；
- `ComponentDoc`、`PageDoc` 的属性和事件命名；
- `ChunkComponent` 返回值的变量名、泛型前缀与 WXML 根节点 `id` 的对应关系；
- 外部工具根据这些信息提供的 WXML 作用域、字段和事件检查。

这些协议不等同于 Annil 运行时 API，但改变它们同样可能破坏消费项目。涉及组件文档、
前缀、Chunk 调用形式或 WXML 识别规则的变更，必须：

1. 先确认实际使用的 `vscode-annil` 或其他外部工具版本；
2. 检查外部工具的实现、测试或版本说明，而不是仅从 Annil 类型文件推断兼容性；
3. 分别验证 Annil 源码/测试支持的框架行为，以及外部工具支持的静态分析行为；
4. 在无法确认外部工具行为时，将影响标记为未知，不把工具约定写成框架运行时规则。

`Wm`、`Vant` 和第三方组件文档应记录上游依据。仓库当前没有完整的上游版本矩阵，不能从类型文件推导精确同步版本。

README 提及 `annil-ui` 和 `annil-test`，但本仓库没有记录正式版本对应表；读取对应仓库前不得推测兼容承诺。

## 6. 当前未定义的政策

仓库尚未正式定义：

- 微信基础库完整支持矩阵；
- 生态仓库版本对应表；
- 类型性能量化预算；
- 所有预发布 tag 的晋升政策；
- 导航数据安全分类。

遇到这些问题时明确标记“仓库未定义”，不要用个人偏好补全。
